# Runtime 前四项可靠性改造

本轮落实结果保存、Spec 检查类型、人工换号恢复、对象及清理关联四项改造。Step Context 决策优化和跨 HITL 预算重构属于后续工作。

## 1. 保存结果与完整证据目录

- 原始证据继续按 Run / Attempt 保存到 `RunEvidence`。结果中的内联元数据最多 200 条，更多证据通过完整目录引用访问，不再把所有附件塞进最终 outcome。
- Agent 协议 v2.24 新增 `attempt-evidence-catalog-v1` 能力。API 在完成时记录目录数量、排序后的 evidenceRef 集合摘要和封存时间。
- `GET /v2/runs/:id/attempts/:attemptId/evidence-catalog` 和对应 Console API 支持 `after` 游标，每页最多 200 条。目录只能读取当前团队、Run、Attempt 的证据。
- Checkpoint 立即幂等保存已接受的验收结果，完成时更新相同的 `(attemptId, criterionId)`。原有事件和 Step Context 留存各次提交历史。
- `finish_verification` 逐项验证结果；一条格式或证据错误不撤销其他有效结果。清理检查发生在有效结果保存之后。
- 受阻执行仍可以展示已通过、已失败和未验证的验收点。清理责任单独记录；未知写入的恢复包装保留原始错误及已有验证结果。

回归覆盖 199、200、201、226、2000、2001 条证据，包括末尾证据引用、强制收尾、清理受阻、重复保存及跨 Attempt 引用拒绝。

## 2. 简洁 Spec 与明确的检查类型

| 要验证的内容       | 契约                                   |
| ------------------ | -------------------------------------- |
| 列表显示“禁用”     | `state.property = TEXT`                |
| 开关处于关闭状态   | `state.property = CHECKED`，期望布尔值 |
| 输入框显示指定值   | `state.property = VALUE`               |
| 请求或响应中的字段 | 仅作 Agent 参考，不进入新验收标准      |

不再因为整句描述出现“开关”就把列表文字改成布尔断言。业务描述保持简洁，属性和证据通道由契约表达。

网络检查显式声明 `method`、`path`、`part`、`field`、`equals`，可通过 `where` 分别限定不同业务对象。`JSON_STRING` 保留字符串与 JSON 对象的类型区别，同时容忍 JSON 内的空白和字段顺序差异。显示标签不参与结构化字段判定。实际引用仍由 `networkCitations` 绑定到已读取的真实请求条目。

当前生成阶段不再生成网络字段验收，也不能将网络字段包装成 DOM 业务检查。上文结构化网络断言仅保留历史协议兼容；新验收以用户可见结果为准，网络采集仍供 Agent 参考和写入核对。

新增 `typed-checks-v1` 能力协商，包含新属性或网络检查的任务只分配给支持它的 Worker。历史 Spec 保持原契约及兼容读取路径，不原地改写。

## 3. 人工换号恢复与并发占用

- DATA_PRECONDITION 人工接管页面增加“更换测试账号后继续”；多角色时选择角色。明确的单账号换号文本也可归一化为 `REPLACE_ACCOUNT`。
- 账号不明确或多角色无法确定时返回具体错误，在校验通过前保留人工浏览器控制权。
- 换号原子更新 Run、任务快照、当前账号绑定与账号版本；清空需要重新核对的前置缺失证明和当前验收观察。
- 旧记录、写入、清理责任、原始证据和历史 Step Context 保留。旧账号的验收结论不直接套用到新账号。
- 当前观察按换号时间划定边界。恢复后不能读取旧绑定作为新账号的当前事实。
- Agent 获得恢复租约前先获取新账号资源占用。同账号冲突时显示 `WAITING / DATA_LOCK`；旧账号占用随原有会话清理流程释放，换号本身不丢弃旧清理责任。
- 重复提交已完成的人工回复维持幂等。

真实 PostgreSQL 回归覆盖两个执行同时换到同一账号的竞争：仅一个准入，另一个等待，旧占用继续保留。

## 4. 对象、请求与清理关联

- Runtime 生成稳定 `recordRef`，关联资源、记录 ID、类型和账号。Agent 可只提交 `recordRef` 与变更字段。
- 身份、已确认归属、初始状态和账号别名不能通过进度更新改写。旧格式的 ID 更新仅在对象唯一时接受。
- DELETE 支持请求体 ID、query `id`、数字或 UUID path ID；相互冲突、重复 query ID、跨资源请求不关联。
- 前置缺失证明要求实际成功查询、明确账号和类型、完整结果。失败的创建回执会使相应缺失证明失效。
- 清理证明关联具体写请求与其后的读取。同一个附件包含创建、删除和删除后查询时可以形成完整证明，无须更换附件 ID。
- 删除后需要精确查询或完整列表确认不存在；分页缺项、旧查询、其他对象的空结果和截断响应均不接受。
- 恢复既有配置要求成功 PUT/PATCH、请求中的初始配置和随后读取的实际配置一致。后续写入或矛盾读取会撤销已过时的清理证明。
- 多条台账更新逐项返回接受或拒绝。一个未知归属对象不影响另一条合法更新。

运行台账保留有限的请求顺序及近期回执，原始网络附件仍完整保存；顺序历史溢出时不凭残缺顺序自动确认清理。无法建立证明的记录继续显示待核对或受阻。

数据库集成使用临时独立 PostgreSQL 数据目录和测试数据库，未使用业务数据库。新增回归覆盖的重点是有效结果不丢失、换号准入、错误证据不通过以及同附件生命周期关联。

本轮尚未执行外部业务网站上的新一轮真实用例，因此不把测试通过数量当作实际成功率提升比例。

本地重测步骤：

1. 重启 `pnpm dev`，使 API 与 Agent 加载 v2.24 协议和新实现。
2. 重新生成 Spec 后开始新的执行，覆盖新检查类型和契约校验；只重试历史 Spec 会继续使用其旧契约。
3. 观察换号后当前账号、逐项结果及清理状态是否一致，并比较新执行的日志。

滚动升级时先更新可读取新旧数据的 API，再更新 Agent。独立部署的 Agent 也需要重启；本轮新增的是 Agent 协议能力。
