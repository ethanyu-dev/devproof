# AI 验收报告与任务结果

任务的最终产物是可追溯的测试报告。`lifecycle` 只描述执行进展，`executionDisposition` 描述是否执行及中断类别，`verdict` 描述产品判定。执行正常结束也可能发现产品问题，执行异常则不能自动转为产品失败。

任务列表分别展示验收项通过、发现产品问题、无法判定、执行受阻、执行异常、尚未执行、超时和取消。已结束任务默认打开测试报告，也可切回用例和日志。详情顶部统计只展示执行进度；验收统计统一在报告中按当前判定与证据计算，避免历史 Run 的空 verdict 掩盖已经记录的失败验收点。发现产品问题与部分用例受阻可以同时成立，不能用汇总的 BLOCKED 丢掉已确认的 FAILED。

## 报告判定

| 总判定          | 条件                                                                                                         |
| --------------- | ------------------------------------------------------------------------------------------------------------ |
| AI 验收通过     | 整个需求范围；来源完整；有结构化需求映射；所有启用环境均覆盖；当前必需验收点全部有证据支持通过；执行正常结束 |
| AI 验收未通过   | 至少一个必需验收点有证据支持 FAILED；其他证据缺口、执行异常同时保留                                          |
| AI 验收无法判定 | 未发现可确认的产品失败，但覆盖、证据、账号/环境前置条件或执行结果不足                                        |
| AI 验收进行中   | 执行尚未结束；报告可展示已有发现，不授予最终通过                                                             |

单独 Case 重跑、直接任务只评价选定范围，通过时显示“本次范围验收通过”，`aiAccepted` 仍为 false。历史规格缺少需求映射时保留 Case 结果，说明无法授予整个需求的通过结论，不反向编造需求。

GitHub CI 检查状态获取失败作为补充信息展示，不作为额外产品验收门槛。只有来源缺口全都属于该已知补充信息、其余需求映射与证据满足要求时，才允许不因这条诊断降级。未知来源缺口仍需处理。

第一版将取消、超时与未执行作为无法完成验收的原因，同时显示其执行状态。INCONCLUSIVE 的既有文字解释原样保留；只有明确缺少当前尝试的判定、引用或必需证据种类时标识“证据不足”，不通过关键词把账号问题推断为产品缺陷。

## 数据来源与接口

`GET /console/api/tasks/:id/acceptance-report` 在调用者的团队内读取规格快照、启用环境、Case 批次、Run 当前尝试、保存的验收判定及证据引用。接口即时返回证据评分，并为终态报告按修订号排队生成 AI 评述；不触发浏览器执行或改写历史判定。

- 对每个当前 Spec Case × 启用环境，只取最大的 executionOrdinal；不能以旧批次的成功覆盖新批次的失败或中断。
- 验收结果与证据必须来自当前 attempt；不混用历史尝试。声明 PASSED/FAILED 但引用缺失或证据种类不足时，报告保留 recordedVerdict，并将报告判定降为无法判定。
- 原始 Run 验收快照负责确定标准；不可变 Spec Case 负责补回需求映射。计划范围中缺少 Run 的项目仍进入报告分母。
- 不把页面步骤、网络观察或过程记忆自动提升为已验证标准。报告汇总经过保存的结果，不重新推断产品结论。
- 报告包含版本、基于内容的修订号、生成时间、来源 hash、需求覆盖、Case 与验收点统计、错误原因、下一步和证据链接。
- Markdown 导出使用同一份报告数据，证据链接走现有鉴权下载接口。导出文本对 Markdown 控制字符进行转义。

报告是读取时生成的结果快照；后续重跑会得到新修订。证据正文仍遵循现有保留期限，历史引用不保证永久可下载。AI 评述存入 task_acceptance_reviews，按任务与报告修订缓存；任务删除时级联删除。报告不作为发布授权。

## 验证与本地开发

重点回归：完整范围通过、部分产品失败与部分执行受阻并存、缺失证据、跨尝试引用、重跑批次、未覆盖需求、多环境缺项、历史规格、取消/超时、当前进度、团队权限与 Markdown 导出。

在隔离目录构建和运行测试，避免运行中的 `node --watch` 被验证构建触发重启。合回主工作区前先确认没有活跃执行，再让本地服务加载代码。

## 任务列表与删除

列表的“执行进度 / 报告”栏在运行中展示进度条，结束后展示验收分数、必需通过项 / 总项数、完成数量与报告入口。分数复用报告的当前 Case、当前尝试及证据校验规则；每页批量读取，不逐条调用模型，也不触发 AI 评述。任务在两次读取间发生变化时暂不展示旧评分。取消、受阻不会显示满格蓝条；没有必需验收点时不显示虚假的 0/100。

已结束任务在列表和详情提供“删除任务”，二次确认后调用 `DELETE /console/api/tasks/:id`，成功返回 204。这是永久删除，删除前会在事务内锁定任务并验证团队归属、终态、所有历史子执行、Spec 分析与浏览器关闭/资源回收状态。并发重试或状态变化会返回 409，运行中、排队中、等待人工的任务不可删除。

删除涵盖全部批次的用例、Spec 快照、执行记录、判定、报告数据、日志、人工交互、通知与专属浏览器轨迹。其他任务共用的证据、浏览器身份和 Runtime 保留；集成事件只保留去重标识，清空任务内容并断开关联，避免历史事件重复创建任务。专属附件与删除重试任务在同一事务提交，提交后立即尝试删除文件，存储暂时不可用时由现有清理 Worker 重试。不会操作被测环境的业务数据，无需数据库迁移。

## 证据评分与 AI 综合评述

- 分数 = 有完整证据的必需通过项 / 全部必需验收点 × 100，向下取整。无法判定、未执行、失败项保留在分母；补充检查不计分。没有必需项时不显示虚假的 0/100。
- 一个 Case 受阻不抹掉该 Case 内已通过的验收点。例如本次 PFRD-3551 的 2 个 Case 中 1 个通过、1 个受阻，但共有 4/5 个必需验收点通过，因此为 80 分，剩余一项需要补验。
- 分数度量已验证程度，不是上线成功概率。全部必需项与需求范围均通过才建议进入上线流程；存在明确的必需产品失败时暂缓上线；未知项或范围缺口存在时补验后再决定。单 Case / 直接任务只评价指定范围。
- 任务结束后的投影自动排队评述；已有任务首次打开报告时补齐。评述使用 SPEC_ANALYSIS Runtime 的空闲槽位及已配置模型，不占浏览器。每次最多 3 个候选模型、每次请求 120 秒；租约 8 分钟，丢失租约最多恢复一次。未知或过期租约不能提交。
- 模型仅收到已保存的规格、结果、摘要和证据引用，不调用浏览器或外部资料。它解释已验证业务能力、产品偏差、未验证风险和具体后续动作；分数、上线门槛和引用由平台再次校验。
- AI 评述与规则建议明确分开标注。模型不可用时仍展示完整评分与验收明细；执行中展示进度评分，全部 Case 结束后才生成最终评述。页面自动刷新评述状态。
- “产品偏差与待验证风险”逐项展示关联需求、验收预期、实际观察、证据、AI 影响评估和下一步，避免把环境/证据问题描述成产品缺陷。Markdown 导出包含同样的信息。
